## 3. 기능 요구사항 (Functional Requirements)

### FR-1. 공고 자동 수집
- **FR-1.1** 매일 1회(KST 새벽, 요약 알림보다 앞선 시각) 아래 소스에서 공고를 수집한다.

  | 소스 | 방식 |
  |---|---|
  | 청약홈 분양정보 (한국부동산원) | data.go.kr `15098547` API |
  | 마이홈포털 임대주택 공고 (LH) | data.go.kr `15088707` API |
  | 마이홈포털 공공임대 단지정보 (국토교통부) | data.go.kr `15110581` API (단지 정보 보강) |
  | SH 서울주택도시공사 | HTML 크롤링 |
  | GH 경기주택도시공사 | HTML 크롤링 |

  > **변경 (2026-10-14, U3 기능 설계 Q1=A)**: 1차 수집 소스는 **청약홈 + LH(15058530 목록 + 15057999 상세) + GH**로 줄였다. SH는 6개 지구가 모두 서울 밖이라 제외, 마이홈 단지정보(15110581)는 공고가 아니라 제외. LH는 cheongYak-radar에서 검증된 API 조합으로 바꿈.
- **FR-1.2** 수집 결과를 공통 스키마로 정규화하고 **소스 + 공고번호 기준으로 upsert**한다 (재실행해도 중복이 생기지 않아야 함).
- **FR-1.3** 한 소스가 실패해도 나머지 소스 수집은 계속하고, 소스별 성공/실패·건수를 실행 로그로 남긴다.
- **FR-1.4** API 키가 없거나 개발 모드일 때는 **목업 응답**으로 동작할 수 있어야 한다.

### FR-2. 3기 신도시 지구 매칭
- **FR-2.1** 기본 지구 6개: 남양주 왕숙1·2, 하남 교산, 고양 창릉, 부천 대장, 인천 계양, 광명 시흥.
- **FR-2.2** 공고명·공급위치·단지명의 **지구 키워드 매칭**과 **시군구 보조 매칭**으로 지구를 판별한다.
- **FR-2.3** 지구 정의(이름·시도·시군구·키워드)는 코드에 하드코딩하지 않고 **설정 테이블**로 관리한다 (1차 UI에서는 6개만 노출).
- **FR-2.4** 어느 지구에도 매칭되지 않는 공고는 저장하지 않거나, 피드 대상에서 제외한다.
- **FR-2.5** 하나의 공고가 여러 지구에 걸치면 모두 연결한다 (예: 광명시흥).

### FR-3. 공급유형 분류
- **FR-3.1** 공고(또는 공고 내 주택형)를 다음 유형으로 분류한다: 공공분양 일반공급, 민영 분양 일반공급(가점/추첨), 고령자 복지주택, 국민임대·영구임대 고령자 우선공급, 행복주택 고령자 계층, 통합공공임대, 무순위·잔여세대, 기타.
- **FR-3.2** 화면에는 전문 용어 옆에 **쉬운 말을 함께 표기**한다 (예: "특별공급" → "우선 신청 물량").

### FR-4. 가구 프로필 입력
- **FR-4.1** 부모님이 직접 입력하는 **단계별 입력 마법사**를 제공한다. 한 화면에 1~2개 항목, 큰 버튼, 이전/다음, 진행 표시.
- **FR-4.2** 입력 항목 (Functional Design에서 최종 확정):

  | 그룹 | 항목 |
  |---|---|
  | 기본 | 본인 생년월일, 배우자 생년월일, 세대 구성(부부 2인 / 기타) |
  | 거주 | 현재 거주 시도·시군구, 해당 지역 거주 기간 |
  | 주택 | 무주택 여부, 무주택 기간, 보유 주택 수 |
  | 청약통장 | 보유 여부, 종류, 가입 기간, 납입 횟수·인정 금액 |
  | 소득·자산 | 월평균 소득(정확한 금액), 총자산, 자동차 가액 (정확한 금액) |
  | 선호 | 관심 지구(다중, 기본 전체), 희망 전용면적, 분양/임대 선호, 저층 선호 |
  | 알림 | 알림 켜기/끄기, 알림 시각(KST, 0~23시 중 1시간 단위, 기본 09시) |

- **FR-4.3** 프로필 원본은 기기(localStorage)에 저장하고, 저장할 때마다 **서버에 device_id로 동기화**한다 (D12).
- **FR-4.4** 설정 화면에서 언제든 항목별로 수정할 수 있고, **"내 정보 모두 지우기"**로 기기와 서버의 프로필을 함께 삭제할 수 있다.
- **FR-4.5** 프로필은 **LLM(Gemini)에 보내지 않는다.**

### FR-5. 자격 판정 엔진
- **FR-5.1** 공고(주택형) × 프로필마다 결과를 **충족 / 미충족 / 확인 필요** 중 하나로 낸다.
  - 확인 필요: 공고에서 요건을 구조화해 뽑지 못했거나, 판정에 필요한 프로필 값이 비어 있는 경우
- **FR-5.2** 판정 기준: 나이(공고 기준일의 만 나이), 무주택 여부·기간, 소득·총자산·자동차 가액 기준, 청약통장 요건, 거주지 요건(해당 시), 세대 구성.
- **FR-5.3** 나이 요건을 지금 충족하지 못하면 **미충족**으로 본다 ("곧 가능" 개념 없음, D6).
- **FR-5.4** 소득·자산 기준(예: 도시근로자 월평균소득 N% 이하)은 **연도별 기준표를 데이터로** 관리하고, 공고 연도에 맞는 표를 적용한다.
- **FR-5.5** 판정 결과마다 **어떤 조건이 맞고 안 맞는지**를 사람이 읽을 수 있는 사유 목록으로 함께 낸다 (상세 화면 표시용).
- **FR-5.6** 판정 로직은 **순수 함수**로 만들어 클라이언트(피드)와 서버(알림)에서 **같은 코드**를 쓴다.
- **FR-5.7** 같은 판정 대상 공고 사이에서는 **추천 점수**(관심 지구, 희망 면적, 분양/임대 선호, 저층 선호, 마감 임박)로 정렬 우선순위를 정한다.

### FR-6. AI 자격조건 요약
- **FR-6.1** 신규 공고마다 Gemini로 **자격조건 요약**과 **노부부 관점 설명**을 쉬운 말로 만든다.
- **FR-6.2** Gemini에는 **공고 정보만** 보낸다 (프로필 제외).
- **FR-6.3** 요약이 실패하면 원문 링크만 보여주고, 다음 수집 때 다시 시도한다.

### FR-7. 맞춤 공고 피드 (`/`)
- **FR-7.1** 관심 지구 + 판정 결과가 **충족 또는 확인 필요**인 공고만 보여준다. **미충족은 숨긴다** (D9).
- **FR-7.2** 카드: 지구, 단지명, 공급유형(쉬운 말 병기), 접수 기간, D-day, NEW 배지, 판정 배지(충족 / 확인 필요).
- **FR-7.3** 기본 정렬: 접수 중 > 접수 예정, 그 안에서는 추천 점수와 마감 임박 순. 마감된 공고는 피드에서 뺀다.
- **FR-7.4** 프로필이 없으면 피드 대신 **입력 마법사 시작** 안내를 보여준다.

### FR-8. 공고 상세 (`/notice/[id]`)
- **FR-8.1** 일정 타임라인(모집공고일·접수·발표·계약), 면적별 공급 세대수, AI 자격조건 요약, 내 판정 결과와 사유, 원문 보기 링크.
- **FR-8.2** **캘린더에 추가** (접수 시작·마감, .ics 또는 플랫폼 캘린더 링크).
- **FR-8.3** 관심 공고(북마크) 추가·해제.
- **FR-8.4** "자녀에게 공유" 기능은 **넣지 않는다** (D17).

### FR-9. 관심 공고 (`/bookmarks`)
- **FR-9.1** 북마크한 공고 목록. 기기(localStorage)에 저장한다.
- **FR-9.2** 마감된 북마크는 "마감" 표시와 함께 남기고, 사용자가 지울 수 있다.

### FR-10. 설정 (`/settings`)
- **FR-10.1** 프로필 항목 수정 (마법사 다시 하기 / 항목별 수정).
- **FR-10.2** 관심 지구 선택 (6개 중 다중 선택).
- **FR-10.3** 알림 켜기/끄기, 알림 시각(KST 1시간 단위).
- **FR-10.4** 화면 모드 전환: 일반 / 쉬운 모드 (D18).
- **FR-10.5** 내 정보 모두 지우기 (FR-4.4).

### FR-11. PWA · Web Push 알림
- **FR-11.1** `manifest.json`과 서비스워커로 **홈 화면 설치**를 지원한다. iOS에는 "홈 화면에 추가" 방법을 그림과 함께 안내한다.
- **FR-11.2** 알림 권한 요청과 푸시 구독을 등록하고, 구독 정보를 device_id에 연결해 서버에 저장한다.
- **FR-11.3** **하루 1회 요약 알림**: 매시 정각에 그 시각을 알림 시각으로 정한 사용자를 골라, 직전 요약 이후 새로 생긴 **충족·확인 필요** 공고가 있으면 "새 공고 N건" 알림을 보낸다. 0건이면 보내지 않는다.
- **FR-11.4** 알림을 누르면 1건일 때는 상세 화면, 여러 건일 때는 피드로 이동한다.
- **FR-11.5** 만료된 구독(404/410)은 자동으로 정리한다.
- **FR-11.6** 마감임박 별도 알림은 **1차 범위에서 제외**한다 (요약만, Q14=B).

## 4. 비기능 요구사항 (Non-Functional Requirements)

### NFR-1. 고령자 접근성 · 사용성
- **NFR-1.1** 일반 모드 본문 **16px 이상** (2026-10-17 사용자 요청으로 변경).  쉬운 모드는 글씨·버튼을 **약 1.25배 이상** 키우고, 정보량은 같게 둔다 (D18).
- **NFR-1.2** 터치 영역 최소 **48×48px**, 충분한 명도 대비(WCAG AA 이상).
- **NFR-1.3** 쉬운 말 우선, 전문 용어는 풀이를 함께 쓴다.
- **NFR-1.4** 주요 동선: 알림 → 상세 → 원문 보기를 **2탭 이내**로.
- **NFR-1.5** 오류 메시지는 무엇을 하면 되는지 한 문장으로 안내한다.

### NFR-2. 개인정보 보호 (최소 보호: Security Extension 미적용, D12·D20)
- **NFR-2.1** 모든 통신은 HTTPS.
- **NFR-2.2** 프로필·푸시 구독 테이블은 **anon 키로 직접 읽거나 쓸 수 없게** RLS로 막고, Edge Function(서비스 역할)을 통해서만 device_id 단위로 접근한다.
- **NFR-2.3** 소득·총자산·자동차 가액 금액은 **암호화된 상태로 저장**하고, 암호화 키는 Supabase Vault / Edge Function 시크릿으로 관리한다 (방식은 NFR Design에서 확정).
- **NFR-2.4** API 키·시크릿은 저장소에 커밋하지 않는다 (`.env*` gitignore).
- **NFR-2.5** 프로필을 로그·LLM·외부 분석 도구로 보내지 않는다.
- **NFR-2.6** 실제 가구 정보가 담긴 문서는 저장소에 올리지 않는다 (`.gitignore`의 로컬 전용 파일 규칙 유지).

### NFR-3. 신뢰성 (Resiliency Extension 미적용, 기본 수준)
- **NFR-3.1** 소스별로 실패를 격리한다 (FR-1.3). 수집 Edge Function이 실패하면 다음 날 실행에 영향을 주지 않는다.
- **NFR-3.2** 수집 upsert와 알림 발송은 **재실행해도 안전**해야 한다 (같은 공고로 같은 날 알림이 두 번 가지 않음).
- **NFR-3.3** 외부 HTML 구조가 바뀌어 크롤링 결과가 0건이면 실행 로그에 경고를 남긴다.

### NFR-4. 성능
- **NFR-4.1** 피드 첫 화면은 모바일 4G 기준 **3초 이내**에 표시한다.
- **NFR-4.2** 일일 수집은 Edge Function 실행 제한 시간 안에 끝나야 한다 (필요하면 소스별로 나눠 호출).

### NFR-5. 운영 · 비용
- **NFR-5.1** Supabase·Vercel **무료 플랜 범위** 안에서 운영하는 것을 목표로 한다.
- **NFR-5.2** cheongYak-radar와 **별도 저장소·별도 Supabase 프로젝트**로 운영한다.
- **NFR-5.3** 스케줄: 수집은 매일 1회(KST 새벽), 알림 발송은 매시 정각(pg_cron).

### NFR-6. 테스트 · 품질 (D19, PBT Extension)
- **NFR-6.1** **Vitest 단위 테스트**: 지구 매칭, 정규화, 공급유형 분류, 자격 판정, 추천 점수, 알림 대상 선정.
- **NFR-6.2** **통합 테스트**: 수집기·Edge Function을 목업 API/HTML 응답으로 테스트한다.
- **NFR-6.3** **E2E 테스트**(Playwright 등): 마법사 입력 → 피드 → 상세 → 북마크 → 설정 변경 흐름.
- **NFR-6.4** **속성 기반 테스트(fast-check)**: PBT-01~10을 지켜야 통과로 본다. 대상 후보는 정규화 멱등성, 직렬화 왕복(프로필·공고), 판정 불변식(예: 소득만 늘리면 충족이 미충족이 될 수는 있어도 그 반대는 없다), 지구 매칭 불변식 등이다.
- **NFR-6.5** 핵심 시나리오는 PBT와 별도로 **예시 기반 테스트**로도 고정한다 (PBT-10).

### NFR-7. 유지보수성
- **NFR-7.1** TypeScript strict 모드.
- **NFR-7.2** 지구 정의, 소득·자산 기준표, 공급유형 매핑은 **데이터로 관리**한다 (코드 수정 없이 갱신).
- **NFR-7.3** cheongYak-radar에서 가져온 모듈에는 출처를 주석이나 문서로 남긴다.
