## Part A. 스토리 분류 방식 (참고용 설명)

| 방식 | 설명 | 장점 | 단점 |
|---|---|---|---|
| 사용자 여정 기반 | 설치 → 프로필 입력 → 알림 받기 → 공고 보기 순서 | 고령 사용자 동선이 잘 보이고 E2E 시나리오로 바로 연결 | 수집·판정 같은 뒤쪽 기능이 흩어짐 |
| 기능 기반 | 수집 / 판정 / 피드 / 상세 / 설정 / 알림 | Unit 나누기와 잘 맞음 | 사용자 흐름이 덜 보임 |
| 페르소나 기반 | 아버지 / 자녀 / 운영자별 | 관점 차이가 분명 | 같은 기능이 여러 곳에 중복 |
| 에픽 기반 | 큰 에픽 아래 작은 스토리 | 범위·진척 관리가 쉬움 | 분류 기준을 따로 정해야 함 |

## Part B. 질문

## Question 1
페르소나를 몇 명으로 잡을까요?

A) 1명: 아버지(실사용자)만

B) 2명: 아버지(실사용자) + 자녀(설치·초기 설정을 도와줌)

C) 3명: 아버지 + 자녀 + 운영자(개발자: 수집 실패 확인, 지구·소득 기준표 갱신)

D) 4명: 위 3명 + 어머니(같은 가구, 별도 기기로 알림 받기)

X) 기타 (아래 [Answer]: 태그 뒤에 설명해 주세요)

[Answer]: 아버지, 어머니

## Question 2
스토리를 어떤 방식으로 묶을까요? (Part A 참고)

A) 에픽 + 사용자 여정: 에픽을 여정 순서(시작하기 → 내 정보 → 공고 받기 → 공고 보기 → 관리)로 두고, 그 아래에 스토리를 배치

B) 에픽 + 기능: 에픽을 기능 단위(수집 / 판정 / 피드 / 상세 / 설정 / 알림)로 두고 스토리를 배치

C) 사용자 여정만 (에픽 없이)

X) 기타 (아래 [Answer]: 태그 뒤에 설명해 주세요)

[Answer]: A

## Question 3
수집·지구 매칭·자격 판정처럼 **사용자가 직접 조작하지 않는 자동 처리**는 어떻게 다룰까요?

A) "시스템/운영자 스토리"로 따로 작성 (예: "운영자로서, SH 수집이 실패하면 로그로 알고 싶다")

B) 사용자 스토리의 인수 기준 안에 녹임 (예: "피드에 내 관심 지구 공고만 보인다"의 인수 기준에 지구 매칭 규칙 포함)

C) 스토리로 쓰지 않고 요구사항(FR)에만 두고, Functional Design에서 다룸

X) 기타 (아래 [Answer]: 태그 뒤에 설명해 주세요)

[Answer]: C

## Question 4
인수 기준(Acceptance Criteria)은 어떤 형식으로 쓸까요?

A) Given / When / Then (시나리오 형식, E2E 테스트로 옮기기 쉬움)

B) 체크리스트 형식 (간결)

C) 핵심 스토리(판정·피드 노출·알림)는 Given/When/Then, 나머지는 체크리스트

X) 기타 (아래 [Answer]: 태그 뒤에 설명해 주세요)

[Answer]: B

## Question 5
스토리 크기는 어느 정도로 할까요?

A) 작게: 화면 하나의 동작 하나 (예: "관심 지구를 고른다", "알림 시각을 바꾼다"). 스토리 수 약 30~40개

B) 중간: 기능 하나 (예: "설정 화면에서 알림을 관리한다"). 스토리 수 약 15~20개

X) 기타 (아래 [Answer]: 태그 뒤에 설명해 주세요)

[Answer]: B

## Question 6
이 앱이 **성공했다**고 볼 기준은 무엇인가요? (인수 기준의 우선순위를 정하는 데 씁니다)

A) **놓치지 않기**: 자격이 되는 3기 신도시 공고를 하나도 놓치지 않고 알림 받기 (판정이 애매하면 보여주는 쪽으로)

B) **혼자 쓰기**: 부모님이 자녀 도움 없이 알림을 받고 공고 내용을 이해하기

C) A와 B 둘 다 똑같이 중요

X) 기타 (아래 [Answer]: 태그 뒤에 설명해 주세요)

[Answer]: A

## Part B-2. 확정된 스토리 작성 방식

| 항목 | 결정 | 근거 |
|---|---|---|
| 페르소나 | **2명: 아버지, 어머니**. 두 분 다 각자 휴대폰에 따로 설치하고, 가구 정보·관심 지구·알림 시각을 각자 입력. 기기끼리는 연결되지 않음 (한 기기에서 "본인"은 그 기기 사용자) | Q1, 추가1=A |
| 묶는 방식 | 에픽 = 여정 순서: E1 시작하기 → E2 내 정보 → E3 공고 받기 → E4 공고 보기 → E5 관리 | Q2=A |
| 자동 처리 | 수집·지구 매칭·판정은 스토리로 쓰지 않음 (FR + Functional Design). 단, **화면에 나타나는 결과**는 인수 기준에 포함 | Q3=C |
| 인수 기준 | 체크리스트 형식 | Q4=B |
| 스토리 크기 | 기능 하나 크기, 약 15~20개 | Q5=B |
| 우선 원칙 | **놓치지 않기**: 판정이 애매하면 숨기지 않고 "확인 필요"로 노출 | Q6=A |
