# U6 pwa-push — 비기능 요구사항

> 근거: 계획 답변 Q1~Q5 = A, Q6 = X(첨부 사진으로 아이콘) (2026-10-16), U6 기능 설계, 요구사항 NFR-1·2·3.2·5, U1·U3 운영 결정
> 대상: `dispatch`(Edge Function), `/api/push/*`(Next), 서비스워커·설치(브라우저)

---

## 1. 성능·시간 예산 (Q3=A)

| ID | 요구사항 |
|---|---|
| NFR-U6-01 | `dispatch` 1회 **60초 이내**. 45초가 지나면 남은 기기는 몫을 잡지 않고 건너뛴다(BR-U6-45) |
| NFR-U6-02 | 동시에 **5개 구독**까지 보낸다. 요청마다 **10초 제한**. 재시도(BR-U6-42)는 2초 뒤 1번 |
| NFR-U6-03 | **한 시각에 기기 1,000대**가 몰려도 NFR-U6-01 안에 끝나는 것을 목표로 한다(대상 조회는 한 번에, 기기별 판정·기록 조회는 묶어서). PBT·통합 테스트에서 1,000대 가짜 발송으로 시간 측정 |
| NFR-U6-04 | 판정 다시 계산(BR-U6-04)은 오래된 기기에만, U2 목표(기기당 1초 이내) 안 |
| NFR-U6-05 | `POST /api/push/subscribe` 서버 처리 500ms 이내(기준선 넣기 포함). `POST /api/push/test`는 푸시 서비스 응답을 기다리므로 10초 이내 |
| NFR-U6-06 | 서비스워커는 페이지 로드를 늦추지 않는다: 첫 화면이 그려진 뒤 등록, 캐시·fetch 처리 없음(BR-U6-94) |

## 2. 신뢰성

| ID | 요구사항 |
|---|---|
| NFR-U6-07 | **멱등**: 같은 시각에 `dispatch`가 겹쳐 실행돼도 기기당 하루 1번, 공고당 1번(BR-U6-21·24). DB 함수의 원자적 갱신으로 보장(설계는 NFR Design) |
| NFR-U6-08 | **기기별 격리**: 한 기기의 판정·발송·기록 실패가 다른 기기 처리를 막지 않는다 |
| NFR-U6-09 | 보냄 → 기록 사이에 실행이 끊기면(시간 초과·중단) 그날 몫은 잡혀 있고 기록은 없을 수 있다 → 그 공고는 다음 날 다시 알린다(중복보다 다시 알림 쪽: 놓치지 않기). 기록은 보낸 직후 바로 쓴다 |
| NFR-U6-10 | 알림 유효 시간(Q4=A): 매일 알림 **TTL 12시간**, 시험 알림 **10분**, 긴급도 `normal` |
| NFR-U6-11 | 만료 구독(404·410)은 그 실행에서 지운다. 7일 넘게 계속 실패한 구독도 지운다(`last_success_at` 기준, 정리 cron) |
| NFR-U6-12 | pg_cron 매시 정각 호출이 빠지면 그 시각은 건너뛴다(BR-U6-23). 호출 실패는 `dispatch_runs`·U3 `invoke_edge_function` 기록에 남는다 |

## 3. 보안

| ID | 요구사항 |
|---|---|
| NFR-U6-13 | `dispatch`는 **비밀 헤더가 맞는 호출만** 받는다(U3와 같은 Vault `cron_secret`) |
| NFR-U6-14 | **구독 주소 제한**: 알려진 푸시 서비스 호스트만 저장(BR-U6-51) — 서버가 사용자가 보낸 임의 주소로 요청하지 않게(SSRF 방지). 발송 직전에도 같은 검사를 한 번 더 |
| NFR-U6-15 | **VAPID 키(Q2=A)**: 개인 키는 Supabase Edge 비밀값·Vercel 환경 변수에만(저장소·로그·응답에 없음). 공개 키만 `GET /api/push/key`로. subject는 앱 주소 `https://mozzi-cheongyak-rador.vercel.app`(이메일 노출 없음). 새어 나갔을 때만 교체 — 교체 절차를 setup 문서에 |
| NFR-U6-16 | 구독 키(`p256dh`·`auth`)·구독 주소는 **로그·오류 응답에 남기지 않는다**. 로그에는 기기 ID·건수·HTTP 상태 코드만 |
| NFR-U6-17 | `POST /api/push/subscribe`·`/test`는 기기 인증(U1), 본문 4KB 제한, 시험 알림 1시간 3번(BR-U6-66) |
| NFR-U6-18 | 서비스워커의 알림 클릭 이동은 같은 사이트 경로만(BR-U6-86) |

## 4. 개인정보 (NFR-2)

| ID | 요구사항 |
|---|---|
| NFR-U6-19 | 알림 내용에는 공고 이름·건수만(BR-U6-35). 푸시 서비스(Google·Apple)는 내용을 볼 수 없다(RFC 8291 암호화) — 그래도 프로필 값은 넣지 않는다 |
| NFR-U6-20 | 구독·알림 기록·시험 기록은 기기를 지우면 함께 지워진다(모두 지우기, 180일 정리 — U1) |
| NFR-U6-21 | 아이콘 원본 사진(가족 반려견)은 공개 저장소에 들어간다 — 사람·집·위치 정보가 없는 얼굴 부분만 잘라 넣는다 |

## 5. 플랫폼 제약 (iOS·Android)

| ID | 요구사항 |
|---|---|
| NFR-U6-22 | iPhone·iPad는 **iOS 16.4 이상, 홈 화면에 추가한 앱에서만** 웹 푸시가 된다 → Safari에서는 설치 안내(BR-U6-61) |
| NFR-U6-23 | iOS는 푸시를 받으면 **반드시 알림을 보여야** 한다(조용한 푸시 금지) → 서비스워커는 내용이 깨져도 기본 문구로 알림을 띄운다 |
| NFR-U6-24 | 권한 요청은 사용자 동작(버튼 누름) 안에서만 — iOS·Chrome 모두 요구 |
| NFR-U6-25 | Android Chrome·삼성 인터넷: 설치 창(`beforeinstallprompt`)이 없을 수 있다 → 글 안내로 대체(BR-U6-73) |
| NFR-U6-26 | 홈 화면 앱 요건: manifest(이름·아이콘 192·512·`standalone`·`start_url`), HTTPS, 서비스워커 |

## 6. 관측성 (Q5=A)

| ID | 요구사항 |
|---|---|
| NFR-U6-27 | `dispatch_runs` 표: 실행마다 1행 — 시작·끝 시각, 시(H), 대상 기기 수, 보냄·건너뜀(0건·이미 보냄)·실패, 지운 구독 수, 다시 계산 수, 시간 예산 초과 여부, 오류 요약(코드만). **30일** 지나면 정리 |
| NFR-U6-28 | 장애 알림은 따로 만들지 않는다(U1 결정). 운영자는 Supabase 표에서 확인 — 확인 쿼리를 setup 문서에 |
| NFR-U6-29 | 구조화 로그(U1 logger): `dispatch.device`(결과·건수), `push.rejected`(상태 코드), `dispatch.time_budget`, `dispatch.recompute.failed` |
