# U6 pwa-push — 업무 규칙

> 근거: 계획 답변 Q1~Q11 = 모두 A (2026-10-16), stories US-01·03·10·11, FR-11, NFR-1.4·3.2, U2 BR-U2-59(노출 조건 K5), U4 BR-U4-16·73~76, U5 BR-U5-04(판정 다시 계산)·K8(이동 경로)
> 날짜·시각은 모두 **한국 시간(KST)** 이다. "오늘"은 발송 실행 시각의 한국 날짜.

---

## 1. 발송 대상 고르기 (US-10, C14)

| ID | 규칙 |
|---|---|
| BR-U6-01 | 발송은 매시 정각에 한 번 실행한다(`dispatch`). 실행 시각의 한국 시(0~23)를 `H`라 한다 |
| BR-U6-02 | 대상 기기 = `notify_enabled = true` **그리고** `notify_hour = H` **그리고** 구독이 1개 이상 **그리고** 오늘 아직 알림을 보내지 않음(`last_push_on ≠ 오늘`) |
| BR-U6-03 | 기기별 알릴 공고 = 이 기기의 판정 중 **`isVisible`(U2 K5)이 참**인 공고(충족·확인 필요, 관심 지구, 마감 아님) **에서** 이미 알림 기록이 있는 공고를 뺀 것. **피드와 같은 함수·같은 오늘**을 쓴다 (US-10 "피드와 똑같다") |
| BR-U6-04 | 판정이 오래됐으면(U5 BR-U5-04와 같은 기준) 그 기기만 먼저 다시 계산한다. 실패하면 남은 판정으로 진행하고 로그 `dispatch.recompute.failed` |
| BR-U6-05 | 알릴 공고가 0건이면 보내지 않고, 오늘 보냄으로 표시하지도 않는다 (같은 날 시각을 바꾸면 그 시각에 다시 확인할 수 있게) |
| BR-U6-06 | **고쳐서 새로 맞게 된 옛 공고도 알린다**(Q2=A): 알림 기록이 없으면 처음 수집 시각과 상관없이 대상이다 |

## 2. 첫 알림의 기준선 (OI-5 결정, Q1=A)

| ID | 규칙 |
|---|---|
| BR-U6-10 | 기기가 **처음으로** 구독을 저장할 때, 그 순간 피드에 보이는 공고(BR-U6-03의 앞부분, 알림 기록과 상관없이)를 알림 기록에 **"기준선"** 으로 넣는다. 첫 알림은 그 뒤에 새로 맞게 된 공고만 센다 |
| BR-U6-11 | "처음"은 기기의 `push_baseline_at`이 비어 있을 때다. 기준선을 넣고 시각을 기록하며, 이후 구독을 다시 저장해도(재구독·구독 변경·만료 후 새 구독) **기준선을 다시 넣지 않는다** — 아직 알리지 않은 공고가 지워지지 않게 |
| BR-U6-12 | 기준선 기록은 "보낸 기록"과 구분해 둔다(`kind = baseline`). 하루 1번 계산·발송 통계에는 넣지 않는다 |
| BR-U6-13 | 프로필이 없는 기기(이론상 없음)는 기준선이 비어도 시각만 기록한다 |

## 3. 하루 1번 (Q4=A, NFR-3.2)

| ID | 규칙 |
|---|---|
| BR-U6-20 | 한 기기에는 **한국 날짜 기준 하루 최대 1번** 보낸다(시험 알림 제외). 오늘 이미 보냈으면 시각을 바꿔도 그날은 더 보내지 않는다 |
| BR-U6-21 | **보내기 전에 오늘 몫을 먼저 잡는다**: `last_push_on`을 오늘로 바꾸는 쓰기가 성공한 실행만 보낸다(같은 시각에 두 번 실행돼도 한 번만 보냄) |
| BR-U6-22 | 모든 구독에 보내기가 실패하면 잡은 몫을 되돌린다(`last_push_on`을 이전 값으로). 공고는 알림 기록이 없으므로 다음 날 함께 알린다 |
| BR-U6-23 | 정한 시각 실행이 통째로 실패하거나 빠지면 그날은 건너뛴다. 다음 정각 실행에서 보충하지 않는다(Q4=A) |
| BR-U6-24 | 같은 공고는 한 기기에 두 번 알리지 않는다: 알림 기록(기기 × 공고)이 있으면 대상이 아니고, 기록은 유일하다 |

## 4. 알림 내용 (Q3=A, US-11)

| ID | 규칙 |
|---|---|
| BR-U6-30 | 제목은 항상 **"모찌네 청약 알리미"** |
| BR-U6-31 | 2건 이상: **"새로 맞는 공고 {N}건이 있어요 ({괄호})"**. 괄호는 충족 a·확인 필요 b가 모두 있으면 "자격 충족 a · 확인 필요 b", 한쪽만 있으면 그쪽만("자격 충족 3") |
| BR-U6-32 | 1건: **"{이름} · {자격 충족 \| 확인 필요} — 눌러서 확인해 보세요"**. 이름은 단지명, 없으면 공고명. 24글자를 넘으면 23글자 + "…" |
| BR-U6-33 | 누르면 갈 곳: 1건 → `/notice/{공고 ID}`, 2건 이상 → `/` (U5 K8). 2건 이상일 때 피드의 NEW는 U5 규칙(열어 보지 않은 7일 이내 공고)으로 붙는다 |
| BR-U6-34 | 같은 날 알림이 겹치지 않게 태그 `daily-{YYYY-MM-DD}`를 붙인다(휴대폰이 같은 태그는 하나로 바꿔 보여 줌) |
| BR-U6-35 | 알림 내용에는 **공고 이름과 건수만** 들어간다. 프로필·금액·판정 사유는 넣지 않는다(NFR-2) |
| BR-U6-36 | 알림 내용 크기는 2KB 이하(푸시 서비스 한도 4KB보다 넉넉히) |

## 5. 보내기·실패 (Q5=A, FR-11.5)

| ID | 규칙 |
|---|---|
| BR-U6-40 | 한 기기의 **모든 구독**에 보낸다. 하나라도 성공하면 그 기기는 "보냄": 알릴 공고 전부를 알림 기록(`kind = sent`)에 넣고, 성공한 구독의 `last_success_at`을 갱신 |
| BR-U6-41 | 응답 404·410(만료) → 그 구독을 지운다. 재시도하지 않는다 |
| BR-U6-42 | 그 밖의 실패(5xx, 429, 네트워크, 시간 초과) → **같은 실행에서 1번 더** 보낸다. 그래도 실패면 그 구독은 실패 |
| BR-U6-43 | 400·401·403·413 등(요청이 잘못됨: 키 문제·내용 크기) → 재시도하지 않고 실패로 기록, 로그 `push.rejected`(상태 코드만) |
| BR-U6-44 | 한 기기 처리 실패가 다른 기기 발송을 막지 않는다(기기별 격리). 실행 결과는 기기 수·보냄·건너뜀·실패·지운 구독 수로 로그·응답에 남긴다 |
| BR-U6-45 | 실행 전체 제한 시간을 넘길 것 같으면 남은 기기는 건너뛴다(잡은 몫이 없으므로 다음 날 다시 대상). 로그 `dispatch.time_budget` |

## 6. 구독 저장 (US-03, Q8=A)

| ID | 규칙 |
|---|---|
| BR-U6-50 | `POST /api/push/subscribe` 본문 = `{ endpoint, keys: { p256dh, auth } }`, 최대 4KB, 다른 키 없음 |
| BR-U6-51 | `endpoint`는 `https:`이고 **알려진 푸시 서비스 주소**여야 한다: `fcm.googleapis.com`, `*.push.apple.com`, `*.push.services.mozilla.com`, `*.notify.windows.com`. 2,048자 이하. 아니면 400 (서버가 임의 주소로 요청을 보내지 않게) |
| BR-U6-52 | `p256dh`는 base64url로 65바이트(0x04로 시작), `auth`는 base64url로 16바이트. 아니면 400 |
| BR-U6-53 | 같은 `endpoint`가 다른 기기에 있으면 이 기기로 옮긴다(같은 브라우저가 기기를 다시 등록한 경우). 같은 기기면 키만 갱신 |
| BR-U6-54 | 기기당 구독은 최대 5개. 넘으면 가장 오래된 것부터 지운다 |
| BR-U6-55 | 저장 뒤 기준선 규칙(BR-U6-10~13)을 적용한다. 응답 200 `{ subscribed: true }` |
| BR-U6-56 | **앱을 열 때마다**(기기 준비 후) 알림 권한이 "허용"이면 지금 브라우저 구독을 서버에 다시 저장한다. 구독이 없으면 조용히 새로 구독해 저장한다. 권한이 "허용"이 아니면 아무것도 하지 않는다(권한 창을 먼저 띄우지 않음, US-03) |
| BR-U6-57 | 서비스워커가 구독 변경 이벤트를 받으면 열린 앱 화면에 다시 저장을 부탁한다(서비스워커는 기기 토큰이 없으므로). 열린 화면이 없으면 다음에 앱을 열 때 BR-U6-56이 처리한다 |

## 7. 알림 켜기 (US-03, U4 연결)

| ID | 규칙 |
|---|---|
| BR-U6-60 | 권한 창은 사용자가 **[알림 받기]·알림 스위치를 눌렀을 때만** 띄운다. 그 전에 "하루 1번, 새 공고가 있을 때만 알려 드려요"를 보여 준다(U4 화면 문구) |

| BR-U6-63 | 설정의 알림 스위치를 켰는데 권한·구독이 없으면 BR-U6-60의 흐름으로 이어 준다(U4 BR-U4-76) |

## 8. 시험 알림 (Q9=A)

| ID | 규칙 |
|---|---|
| BR-U6-65 | 설정에 [시험 알림 보내기]. 누르면 이 기기의 모든 구독으로 바로 "알림이 잘 와요 — 새 공고가 있으면 이렇게 알려 드려요"를 보낸다. 누르면 이동할 곳은 `/settings` |
| BR-U6-66 | 기기당 **최근 1시간에 3번**까지. 넘으면 429 `TOO_MANY_TESTS` "잠시 뒤에 다시 시험해 주세요" |
| BR-U6-67 | 구독이 없으면 409 `NO_SUBSCRIPTION` "먼저 알림을 켜 주세요". 시험 알림은 알림 기록·하루 1번 계산에 넣지 않는다. 만료 응답이면 그 구독을 지운다 |
| BR-U6-68 | 결과 문구: 하나라도 보냄 → "시험 알림을 보냈어요. 잠시 뒤 알림이 오는지 확인해 주세요" / 모두 실패 → "알림을 보내지 못했어요. 알림을 다시 켜 주세요" |

| BR-U6-74 | iPhone·iPad(Safari): 그림 3장 단계 안내 — ① 아래 가운데 공유 버튼(네모에 위쪽 화살표) ② 메뉴를 올려 "홈 화면에 추가" ③ 오른쪽 위 "추가". 각 그림 아래 큰 글씨 설명. Safari가 아닌 iPhone 브라우저면 "Safari로 열어 주세요"를 먼저 |
| BR-U6-75 | 홈 화면 이름·앱 이름 모두 **"모찌네 청약 알리미"** (2026-10-17 사용자 요청으로 변경). 아이콘은 파란 바탕 + 집 모양(지금 SVG를 PNG 192·512, 여백 있는 maskable, iPhone용 180)으로 |
| BR-U6-76 | 안내 띠 닫기 기록은 개인 정보가 아니므로 "모두 지우기"에서 지우지 않는다(화면 모드와 같이 남김) |

## 12. API (S5·S6)

공통: 오류 형식 `{ code, message }`(U1), `cache-control: no-store`. 로그에는 기기 ID·건수·상태 코드만 — **구독 주소·키·알림 내용은 남기지 않는다**.

| ID | API | 규칙 |
|---|---|---|
| BR-U6-90 | `POST /api/push/subscribe` | 기기 인증. §6 |
| BR-U6-91 | `POST /api/push/test` | 기기 인증, 본문 없음. §8. 200 `{ sent, failed, removed }` |
| BR-U6-92 | `GET /api/push/key` | 인증 없음. 200 `{ publicKey }`(VAPID 공개 키) — 공개 값 |
| BR-U6-93 | `dispatch` (Edge Function) | 비밀 헤더(U3 `CRON_SECRET`와 같은 방식) 없으면 401. 결과 `{ hour, devices, sent, skipped, failed, removedSubscriptions, recomputed }` |
| BR-U6-94 | 서비스워커 `sw.js` | 페이지 응답을 저장(캐시)하지 않는다 — 공고·판정이 오래된 화면을 보이지 않게. 알림 표시·클릭·구독 변경만 맡는다 |

## 13. 속성 기반 테스트 대상 (PBT-01 식별)

상세는 domain-entities §7. 순수 함수로 떼어 낸다: 발송 계획(대상 기기·알릴 공고), 하루 1번 몫 잡기·되돌리기, 알림 문구·이동 주소, 발송 결과 정리(보냄·만료·실패), 구독 형식 검사, 기준선, 시험 알림 한도, 설치 안내 표시 여부, 클릭 주소 검사.
