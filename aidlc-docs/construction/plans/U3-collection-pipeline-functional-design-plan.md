# U3 collection-pipeline — 기능 설계 계획

**Unit 범위** (unit-of-work.md): 매일 수집 Edge Function `collect` — 소스별 수집, 정규화, 지구 매칭(U2), 공급유형 분류(U2), AI 요약·요건 추출(Gemini, 공고 정보만), 요건 확정(U2), 대표 공고 묶음 저장(U1 RPC), 전체 판정 재계산(U2), 실행 기록. 마지막에 **실제 공고 골든 세트**(NFR-U2-07)
**관련 스토리**: US-10·12·13·15의 데이터
**열린 이슈**: OI-U2-1(지구 동 키워드를 실제 공고로 확인), OI-4(수집 시각 — Infrastructure Design에서)

**cheongYak-radar에서 확인한 사실** (`../cheongYak-radar/supabase/functions/collect/`)
- 청약홈: odcloud `ApplyhomeInfoDetailSvc/v1/getAPTLttotPblancDetail` (data.go.kr 15098547), 최신순 300건 스캔
- LH: **SPEC의 15088707이 아니라** `lhLeaseNoticeInfo1`(data.go.kr **15058530**, 공고 목록) + `lhLeaseNoticeDtlInfo1`(**15057999**, 공급일정) 조합으로 동작했음. 목록에 접수 시작일이 없어 상세 조회가 필요
- GH: odcloud 데이터셋엔 접수일이 없어 **청약센터 메인 화면 크롤링**으로 바꿨음 (대기열 걸리면 그날은 건너뜀)
- SH: 서울주거포털 목록 + 상세 본문 크롤링
- Gemini: `gemini-2.5-flash`로 공고 **PDF**를 읽어 JSON 추출 (사고 토큰이 출력 예산을 잡아먹는 문제 대응 경험 있음)

### Q2. AI 요건 추출은 무엇을 읽게 할까요?
공고의 상세 자격 요건(소득 %, 자산 한도 등)은 대부분 **공고문 PDF**에만 있습니다. API·HTML 목록에는 거의 없습니다.

A) **공고문 PDF**: 새 공고(또는 내용이 바뀐 공고)마다 PDF를 내려받아 Gemini가 읽음. 정확하지만 공고마다 호출 1번, PDF를 못 찾으면 추출 없이 표준 요건만 사용 **(추천: 정밀 판정 D7의 핵심)**

B) API·HTML에 있는 텍스트만: 호출이 가볍지만 추출되는 요건이 거의 없어 대부분 표준 요건으로 판정

C) 1차에서는 추출하지 않고 표준 요건만 사용 (요약도 PDF 없이 공고명·일정으로만)

X) 기타 (아래 [Answer]: 태그 뒤에 설명해 주세요)

[Answer]: A

### Q3. 같은 공고가 여러 소스에 나올 때 묶는 기준 (U1 Q1=A 대표 공고)
예: LH 공공분양이 청약홈과 LH 목록에 둘 다 나옴. 공고명이 소스마다 조금씩 다름("하남교산 A2블록 공공분양" vs "[하남교산] A-2BL 뉴:홈").

A) **지구 + 블록 번호 + 모집공고일**: 공고명에서 블록 번호(A2, A-2BL, A2블록 → `A2`)를 뽑아, 같은 지구·같은 블록·같은 모집공고일이면 같은 공고로 묶음. 블록 번호가 없으면 묶지 않음(소스별 따로) **(추천: 3기 신도시 공고는 대부분 블록 번호가 있음)**

B) 묶지 않음: 소스별로 따로 보여줌 (같은 공고가 두 번 보일 수 있음, 알림 수도 2배)

X) 기타 (아래 [Answer]: 태그 뒤에 설명해 주세요)
