## 질문

### Q1. 휴대폰에서 API 호출이 네트워크 오류로 실패하면 다시 시도할까요?

A) **1번만 자동 재시도**: 네트워크 오류나 5xx면 1초 뒤 1번 다시 시도. 이 앱의 API는 다시 보내도 결과가 같게(멱등) 설계되어 있음(조회, 덮어쓰기 저장, 삭제). 그래도 실패하면 오류 안내 + [다시 시도] 버튼 **(추천)**

B) 자동 재시도 없이 바로 오류 안내 + [다시 시도] 버튼

C) 최대 3번 재시도 (1초 → 2초 → 4초 간격)

X) 기타 (아래 [Answer]: 태그 뒤에 설명해 주세요)

[Answer]: A

### Q2. 지구 목록·공급유형 이름 같은 기준 데이터를 캐시할까요?
이 데이터는 거의 바뀌지 않지만, 마법사·피드·상세에서 자주 읽습니다.

A) **서버 메모리에 10분 캐시**: Next 서버 함수 인스턴스 안에서 10분 보관. 시드를 바꾸면 최대 10분 뒤 반영 **(추천)**

B) 캐시 없음: 매번 DB에서 읽음 (규모가 작아 성능 차이 거의 없음, 가장 단순)

C) 빌드할 때 화면 코드에 넣음: DB 값을 바꾸면 다시 배포해야 반영

X) 기타 (아래 [Answer]: 태그 뒤에 설명해 주세요)

[Answer]: A

### Q3. 누구나 기기를 등록할 수 있는데(Q4=B), 대량 등록은 막을까요?

A) **DB 기준 전체 한도**: 최근 1시간 동안 새로 등록된 기기가 20대를 넘으면 등록을 잠시 막음(429). 가족 규모에서는 걸릴 일이 없고, 서버 인스턴스가 여러 개여도 정확함 **(추천)**

B) 막지 않음 (요청 본문 크기 제한만, RK-U1-1 위험 그대로 감수)

C) IP별 한도 (서버리스는 인스턴스마다 메모리가 따로라 정확하지 않음)

X) 기타 (아래 [Answer]: 태그 뒤에 설명해 주세요)

[Answer]: A

### Q4. DB에 여러 단계로 쓰는 작업을 어떻게 원자적으로 처리할까요?
예: 판정 교체(기기의 기존 판정 삭제 + 새 판정 입력), 공고 upsert(원천 공고 + 대표 공고 + 주택형 + 지구 연결), 모두 지우기.

A) **DB 함수(RPC)로 묶기**: supabase-js로 접근하되, 여러 단계 쓰기는 PostgreSQL 함수 하나로 만들어 한 트랜잭션에서 실행. Node·Deno 양쪽에서 같은 함수를 호출 **(추천)**

B) Postgres 드라이버로 직접 연결해 코드에서 트랜잭션 처리 (서버리스에서 연결 풀 관리가 필요하고, Deno·Node 드라이버가 다름)

C) 원자성 없이 순서대로 실행하고, 중간 실패는 다음 실행에서 바로잡힘에 기대기

X) 기타 (아래 [Answer]: 태그 뒤에 설명해 주세요)

[Answer]: A
