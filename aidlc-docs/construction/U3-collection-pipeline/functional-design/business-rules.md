## 2. 정규화

| ID | 규칙 |
|---|---|
| BR-U3-10 | 날짜는 `YYYYMMDD`, `YYYY.MM.DD`, `YYYY-MM-DD`, `YYYY/MM/DD`, 뒤에 붙은 시각·요일을 받아 한국 날짜 `YYYY-MM-DD`로. 해석 못 하면 null |
| BR-U3-11 | 접수 시작은 특별공급 시작이 있으면 그 날짜, 없으면 일반 접수 시작 (청약홈) |

| BR-U3-14 | 문자열은 앞뒤 공백 제거, 빈 문자열은 null. 번호·제목이 비면 그 원천 공고는 버린다 |

## 4. 대표 공고 묶기 (Q3=A, U1 BR-U1-23·24)

| ID | 규칙 |
|---|---|
| BR-U3-30 | **블록 키**: 제목·단지명에서 `영문 1~2자 + (하이픈) + 숫자 1~2자리 (+ -숫자)` 뒤에 `블록`·`BL`·`bl`이 붙은 부분을 찾아 대문자·하이픈 제거로 맞춘다. 예: `A2블록`·`A-2BL`·`a2 BL` → `A2`, `S-1블록` → `S1`, `A1-1블록` → `A11`이 아니라 `A1-1`(두 번째 숫자는 하이픈 유지). 여러 개면 정렬해 `+`로 잇는다 (`A1+A2`) |
| BR-U3-31 | **묶음 키**: 블록 키·지구·모집공고일이 모두 있으면 `{지구들(정렬, +)}|{블록 키}|{모집공고일}`. 하나라도 없으면 `{source}:{sourceNoticeNo}` (묶지 않음) |
| BR-U3-32 | 같은 묶음 키의 원천 공고는 하나의 대표 공고로 저장하고 원천 공고는 모두 `source_notices`에 연결 |
| BR-U3-33 | 대표(primary) 선택 우선순위: **공급 기관 원문(LH·GH) > 청약홈**. 같은 우선순위면 `sourceNoticeNo` 사전순. 대표의 제목·링크·일정을 쓰되, 대표에 없는 일정은 다른 원천에서 채운다 |
| BR-U3-34 | 묶음 결과는 입력 순서와 무관하다 |

## 6. 변경 감지·재처리 (Q5=A)

| ID | 규칙 |
|---|---|
| BR-U3-50 | `contentHash` = SHA-256(정규화 필드: 제목, 위치, 공급유형 문자열, 일정 6개, 첨부 URL 목록). `raw`·조회 시각처럼 매번 바뀌는 값은 넣지 않는다 |
| BR-U3-51 | 묶음의 모든 원천 공고 해시가 저장된 값과 같고 AI 처리가 끝났으면(`summary_status = done`) **아무것도 쓰지 않는다** |
| BR-U3-52 | 해시가 하나라도 다르거나 새 공고면 → 정규화 결과로 묶음을 다시 만들고 AI 추출·요약을 다시 한 뒤 저장 |
| BR-U3-53 | 해시가 같아도 `summary_status`가 `pending`/`failed`이고 `ai_attempts < 3`이면 AI만 다시 시도 (FR-6.3) |
| BR-U3-54 | 판정은 개별로 다시 계산하지 않고, 수집이 끝난 뒤 U2 `recomputeAll` 한 번으로 반영 |
| BR-U3-55 | AI 시도마다 `ai_attempts + 1`. 3번 실패하면 더 시도하지 않고 표준 요건·요약 없음(`failed`)으로 둔다 — 화면은 "요약을 준비 중이에요" 대신 원문 보기 안내 (U5) |

## 7. AI 추출·요약 (Q2=A, AD-7, FR-6)

| ID | 규칙 |
|---|---|
| BR-U3-60 | **공고문 PDF 찾기**: 첨부 중 이름이 `공고문` > `공고` > `모집`인 PDF를 우선(포스터·팸플릿·주택내역·연락처·신청서 같은 부속 자료는 뒤로 — Step 12 실제 GH 첨부로 보완), 없으면 첫 PDF. 묶음이면 대표 원천부터 찾는다. PDF가 없으면 AI 추출 없이 진행(표준 요건, 요약 `failed`) |
| BR-U3-61 | PDF 크기 상한 20MB (Gemini 인라인 한도). 넘으면 추출하지 않는다 |
| BR-U3-62 | 프롬프트는 공고 정보(PDF·제목·공급유형 후보)만 넣고 **프로필·가족 정보는 넣지 않는다** (FR-4.5). PDF 내용은 지시가 아니라 자료로 다룬다고 명시한다 |
| BR-U3-63 | 응답은 JSON만 받는다(구조화 출력). 문서에 없는 값은 null, 추측 금지, 금액 단위(소득 %, 자산·자동차 만원)·시도 줄임 이름을 프롬프트에 명시 |
| BR-U3-64 | 검증: `isNotice=false`면 요건·요약을 버리고 표준 요건만. 주택형 `requirements`는 U2 `validateRequirements` 통과분만 사용(실패 → 그 주택형은 표준 요건). 요약은 문자열·길이(각 600자)만 확인 |
| BR-U3-65 | **주택형 만들기**: 추출 주택형이 있으면 각각 `classifySupplyType(supplyTypeText)`로 유형을 정하고, 요건 = U2 `resolveRequirements(표준(유형), 추출)`. 추출 주택형이 없으면 공고 공급유형으로 주택형 1개(면적·세대수 null, 표준 요건) |
| BR-U3-66 | 추출 일정은 소스 일정이 비어 있을 때만 채운다 (소스 값 우선) |
| BR-U3-67 | 한 번 실행에서 AI 호출 수 상한을 둔다 (값은 NFR Requirements). 넘친 공고는 `pending`으로 다음 실행에 처리 |

### 10.2 공고 지역 판별

| ID | 규칙 |
|---|---|
| BR-U3-C4 | 정규화의 시도(`sido`)가 수도권이면 지역을 만든다. 시군구는 U2 공용 목록에 맞춘다: ① 그대로 목록에 있으면 그 값 ② "고양시 덕양구"처럼 시 + 구면 **시** ③ 인천 옛 구는 새 구로(BR-U3-C5) ④ 못 맞추면 `sigungu: null`(시도까지만) |
| BR-U3-C5 | **인천 옛 구 → 새 구**: 동구 → 제물포구. 중구 → 주소·제목에 영종 쪽 동(domain-entities 표)이 있으면 영종구, 아니면 제물포구. 서구 → 검단 쪽 동이 있으면 검단구, 아니면 서해구. 주소에 동이 없어 가를 수 없으면 `sigungu: null` |
| BR-U3-C6 | 여러 시도·시군구에 걸친 공고(통합 공고)는 찾은 수도권 지역을 모두 담는다. 같은 시도에 시군구 값과 null이 함께 나오면 시군구 값만 남긴다 |
| BR-U3-C7 | 묶음(여러 원천 → 대표 공고 1개)의 지역 = 원천 지역의 합집합(BR-U3-C6 정리 규칙 적용) |
| BR-U3-C8 | 지구가 맞은 공고는 그 지구의 시도·시군구(첫 시군구)도 지역에 넣는다 (예: 하남 교산 → 경기 하남시) — 지구 밖 관심 시군구로 고른 사람에게도 보이게 |
| BR-U3-C9 | **AI 분석으로 지역 고치기 (Q2=A)**: Gemini 응답의 공급 위치 시군구(`supplySigungu`, 여러 개 가능)를 BR-U3-C4로 맞춘 값이 있으면, 그 시도의 `sigungu: null` 항목을 그 값들로 바꿔 저장한다. 시군구가 이미 정해진 항목은 바꾸지 않는다(소스 값 우선, BR-U3-66과 같은 원칙). 다음 수집이 다시 시도까지만으로 덮지 않도록, 수집 저장 때 **AI가 고친 지역은 유지**한다 |
