# U5 feed-detail — 업무 규칙

> 근거: 계획 답변 Q1~Q12 = 모두 A (2026-10-16), stories US-11~17, U2 BR-U2-59(노출 조건 K5)·BR-U2-60~65(점수·정렬), U2 messages(사유·행동 문구), U3 요약 형식, U4 기기 저장 키, U1 BR-U1-20(오류 형식)
> 판정은 **계산하지 않고 읽기만** 한다(AD-3). 이 문서는 피드·상세·관심 공고의 **노출·정렬·표시·저장** 규칙을 정한다.
> 날짜는 모두 **한국 날짜(KST)** 로 계산한다. "오늘"은 서버 응답의 `today`, 저장본을 다시 그릴 때는 기기의 한국 날짜를 쓴다.

## 1. 피드 노출 (US-12, FR-7)

| ID | 규칙 |
|---|---|
| BR-U5-01 | 피드에 나오는 공고 = 이 기기의 판정 중 `isVisible({ verdict, inDistrict, status })`가 참인 것 (U2 BR-U2-59). 즉 미충족 숨김, 관심 지구 밖 숨김, 마감 제외. **알림(U6)과 같은 함수를 쓴다** |
| BR-U5-02 | `status`는 U2 `noticeStatus(공고 일정, 오늘)`. 마감일이 없으면 마감으로 보지 않는다(놓치지 않기) |
| BR-U5-03 | 프로필이 없는 기기는 피드 대신 처음 실행 안내(U4 HomeGate). 피드 API는 `state: "no_profile"`과 빈 목록을 준다 |
| BR-U5-04 | **판정이 최신이 아니면 피드 API가 그 자리에서 한 번 다시 계산한다**: 서버 프로필은 있는데 ① 판정이 하나도 없고 보관 중인 공고는 있거나 ② 판정의 `profile_version`이 현재 프로필 버전보다 낮으면 `recomputeForDevice(오늘)` 실행 후 다시 읽는다. 다시 계산이 실패하면 남아 있는 판정으로 응답하고 `state: "outdated"` (Q5=A) |
| BR-U5-05 | 같은 요청에서 다시 계산은 최대 1번. 실패는 로그 `feed.recompute.failed`(기기 ID·오류 코드만) |

## 4. D-day (Q3=A)

`d(x) = x − 오늘` (일 수). 위에서부터 처음 맞는 줄을 쓴다.

| ID | 조건 | 표시 | 강조 |
|---|---|---|---|
| BR-U5-30 | 마감(closed) | "접수 마감" | – |
| BR-U5-31 | 접수 중, 마감일 = 오늘 | "오늘 마감" | 빨간색 |
| BR-U5-32 | 접수 중, 시작일 = 오늘 | "오늘 접수 시작" | – |
| BR-U5-33 | 접수 중, 마감일 있음 | "마감까지 D-{d(마감일)}" | d ≤ 3이면 빨간색 |
| BR-U5-34 | 접수 중, 마감일 없음 | "접수 중 (마감일 미정)" | – |
| BR-U5-35 | 접수 예정, 시작일 있음 | "접수까지 D-{d(시작일)}" | – |
| BR-U5-36 | 접수 예정, 시작일 없음 | "일정 미정" | – |

- BR-U5-37: 표시되는 D 숫자는 항상 1 이상이다(0은 "오늘 …" 문구, 음수는 나오지 않음).
- BR-U5-38: 빨간색 강조에는 글자("오늘 마감", "D-2")가 함께 있으므로 색에만 의존하지 않는다.

## 5. NEW 배지 (Q2=A)

| ID | 규칙 |
|---|---|
| BR-U5-40 | NEW = **처음 수집 시각(`first_seen_at`)이 지금부터 7×24시간 이내**이고, **이 기기에서 상세를 아직 열지 않은** 공고 |
| BR-U5-41 | 상세 화면을 열면(응답을 받아 그린 뒤) 그 공고를 "열어 본 공고"(`mz.seen`)에 넣는다. 피드에서 카드만 본 것은 열어 본 것이 아니다 |
| BR-U5-42 | 열어 본 기록은 기기에만 있고 서버로 보내지 않는다. 14일이 지난 기록과 500개를 넘는 오래된 기록은 저장할 때 지운다 |
| BR-U5-43 | 기록을 읽을 수 없으면(깨짐) 빈 기록으로 본다 — 모두 NEW로 보일 수는 있어도 오류로 멈추지 않는다 |

## 6. 피드 저장본 (Q6=A, NFR-4.1)

| ID | 규칙 |
|---|---|
| BR-U5-50 | 피드 API 응답(`ready`·`outdated`일 때)을 기기에 저장한다(`mz.feed`). 다음에 열 때 **저장본을 먼저 그리고** 새 응답을 받으면 바꾼다 |
| BR-U5-51 | 저장본을 보이는 동안 "새 공고를 확인하고 있어요"를 작게 표시. 받아 오기에 실패하면 저장본을 그대로 두고 "인터넷 연결을 확인해 주세요. {저장 시각}에 확인한 목록이에요" + [다시 시도] |
| BR-U5-52 | 저장본을 그릴 때 기기의 오늘 날짜로 상태·D-day를 다시 계산하고, **마감된 공고는 뺀다**. 새로 나타나게 하지는 않는다 |
| BR-U5-53 | 저장본에는 공고 정보와 판정 결과(충족·확인 필요)·점수만 있고 **내 금액·프로필은 없다**. 그래도 판정은 개인 정보에 가까우므로 모두 지우기(U4 BR-U4-94)에서 함께 지운다 |
| BR-U5-54 | 내 정보를 저장(마법사·고치기)하면 저장본을 지운다 — 바뀐 정보로 계산한 결과만 보이게 |
| BR-U5-55 | 형식이 깨졌거나 버전이 다른 저장본은 버린다 |

### 8.1 일정 타임라인

| ID | 규칙 |
|---|---|
| BR-U5-75 | 단계(고정 순서): 모집공고 `announced_at` → 접수 시작 `apply_start` → 접수 마감 `apply_end` → 당첨 발표 `result_at` → 계약 `contract_start`(~`contract_end`). 날짜가 없는 단계도 "미정"으로 보인다 |
| BR-U5-76 | 각 단계는 지난 단계(날짜 < 오늘) / 오늘 / 다가올 단계로 표시한다. 글자로도 구분("지남", "오늘") |
| BR-U5-77 | "오늘" 표시는 **날짜가 오늘 이하인 마지막 단계 바로 뒤**에 둔다(오늘인 단계가 있으면 그 단계에 표시). 날짜 있는 단계가 모두 미래면 맨 앞. 데이터 순서가 어긋나도 단계 순서는 바꾸지 않는다 |

### 8.2 면적별 세대수 (Q9=A)

| ID | 규칙 |
|---|---|
| BR-U5-78 | 표의 줄 = 주택형. 열: 주택형(이름 없으면 면적), 공급유형(쉬운 말), 면적, 세대수 |
| BR-U5-79 | 면적 = **"전용 59㎡ (약 18평)"**: 평 = 전용면적 × 0.3025를 반올림한 정수(1평 미만이면 소수 첫째 자리). ㎡는 소수점 이하가 0이면 생략, 아니면 둘째 자리까지. 면적이 없으면 "면적 미정" |
| BR-U5-80 | 세대수가 없으면 "-". 맨 아래 합계는 아는 세대수만 더하고, 모르는 줄이 있으면 "{합}세대 이상" |
| BR-U5-81 | 줄 순서: 면적 작은 순(없으면 뒤), 같으면 주택형 이름 순 |

## 9. 판정 이유 (US-14, Q7=A·Q8=A)

| ID | 규칙 |
|---|---|
| BR-U5-85 | 맨 위 한 줄 요약: 충족 "이 공고에 신청할 수 있어 보여요", 확인 필요 "신청할 수 있는지 확인이 필요해요", 미충족 "지금 조건으로는 신청이 어려워요" |
| BR-U5-86 | **묶기**: 주택형 판정을 공급유형별로 모은다. 한 공급유형 안의 주택형들이 **판정과 조건 줄(키·판정·사유·행동)이 모두 같으면 한 덩어리**로 보이고 면적만 나열("전용 59㎡, 74㎡, 84㎡"). 하나라도 다르면 그 공급유형은 주택형별로 나눈다 |
| BR-U5-87 | 덩어리 순서: 충족 → 확인 필요 → 미충족, 같은 판정 안에서는 공급유형 쉬운 말 이름 순. **미충족 덩어리는 "신청이 어려운 유형 N개" 아래 접어 둔다**(눌러서 펼침). 충족·확인 필요가 하나도 없으면 미충족을 펼쳐 둔다 |
| BR-U5-88 | 조건 한 줄: "✔ 맞음 / ✖ 안 맞음 / ? 확인 필요" 기호 + 글자(화면 낭독기용 "맞음/안 맞음/확인 필요") + 조건 이름 + 사유. 예: "✔ 나이: 만 65세 이상 → 만 66세예요" |
| BR-U5-89 | 확인 필요 줄에는 행동 문구(`action`)를 바로 아래에 붙인다. "설정에서 …" 문구에는 해당 설정 고치기 링크를 단다 |
| BR-U5-90 | **내 금액 붙이기**: 조건에 `userValue`(월소득·총자산·자동차)가 있고 기기 프로필에 그 값이 있으면 줄 끝에 "→ 입력하신 금액 월 450만원"을 붙인다(U4 한글 금액 표기). 값이 없으면 붙이지 않는다. **내 금액은 서버로 보내거나 저장본에 넣지 않는다** |
| BR-U5-91 | 판정이 최신 프로필로 계산되지 않았으면(`outdated`) "최근 바꾼 내 정보가 아직 반영되지 않았어요" |
| BR-U5-92 | 항상 아래에 "참고용이며 최종 자격은 공고문과 기관 확인이 필요합니다" |

조건 이름: type 공급 유형, age 나이, homeless 무주택, income 소득, asset 자산, car 자동차, savings 청약통장, residence 사는 곳, household 세대 구성, welfare 복지 대상.

| BR-U5-102 | 주소가 `http:`·`https:`가 아니면 쓰지 않는다. 대표 출처 주소가 쓸 수 없으면 다른 출처 중 첫 번째를 대표로 올린다. 하나도 없으면 버튼을 비활성 "원문 주소가 없어요" |
| BR-U5-103 | 원문은 새 창(브라우저)으로 연다(`rel="noopener noreferrer"`) |

## 14. API (S4)

공통: 응답 오류는 `{ code, message }`(U1 BR-U1-20), `cache-control: no-store`. 로그에는 요청 ID·기기 ID·결과·걸린 시간·건수만(**판정 내용·프로필 없음**).

| ID | API | 규칙 |
|---|---|---|
| BR-U5-130 | `GET /api/feed` | 기기 인증 필수. 쿼리 없음. 200 `{ state, today, generatedAt, items }`(domain-entities §2). 노출·정렬은 §1·§2 |
| BR-U5-131 | `GET /api/notices/[id]` | 기기 인증 필수. `id`가 UUID 형식이 아니면 404 `NOT_FOUND`(DB 조회 안 함). 없는 공고 404. 200 `{ today, notice, judgement }` — 판정이 없으면 `judgement: null`, 프로필이 없으면 `profile: "none"` |
| BR-U5-132 | `GET /api/notices?ids=` | 기기 인증 필수. 쉼표로 나눈 UUID **1~100개**(중복 제거). 형식이 틀린 ID가 있거나 개수를 넘으면 400. 200 `{ today, items, missing }` — 관심 공고 갱신용 요약만(판정 없음) |
| BR-U5-133 | `GET /api/notices/[id]/calendar` | 인증 없음(공고 정보만). 시작·마감일이 없거나 없는 공고면 404. 200 `text/calendar; charset=utf-8`, `content-disposition: attachment; filename="cheongyak-{id 앞 8자}.ics"` |
| BR-U5-134 | 응답에 넣지 않는 것 | 원천 응답 원본(`raw`), 첨부 목록, 요건 원본(`requirements`), AI 처리 정보(`ai_*`), 다른 기기의 판정 |
