# U1 setup-data-platform — 비기능 설계 패턴

> 근거: U1 NFR Design 계획 답변 (Q1=A 1회 자동 재시도, Q2=A 서버 메모리 10분 캐시, Q3=A DB 기준 등록 한도, Q4=A DB 함수(RPC)로 원자적 쓰기)
> 요구사항 대응: NFR-U1-01~29

---

## 1. 복원력 (Resilience)

### P-R1 단일 재시도 + 사용자 재시도 (Q1=A)
| 항목 | 설계 |
|---|---|
| 대상 | 클라이언트 `apiFetch`의 모든 호출 |
| 재시도 조건 | 네트워크 오류(fetch 예외), 응답 5xx, 408 |
| 재시도 안 함 | 4xx(400·401·409·413·429). 401은 재시도 대신 재등록 흐름(BR-U1-09) |
| 횟수·간격 | **1회, 1초 후** |
| 그래도 실패 | `{ code: 'NETWORK', message: '인터넷 연결을 확인해 주세요' }`를 화면에 넘김 → ErrorMessage + [다시 시도] |
| 안전 근거 | 모든 기기 API는 멱등: 조회(GET), 덮어쓰기(PUT), 삭제(DELETE, 없어도 204), 등록(POST: 같은 ID·같은 토큰이면 200, **BR-U1-03 보완**) |

### P-R2 기기 우선(오프라인 우선) 로컬 기능
- 등록된 기기는 네트워크 없이 앱 뼈대를 표시한다 (NFR-U1-05)
- 프로필·관심 공고·화면 모드는 localStorage가 원본이라 서버 장애 중에도 보인다 (NFR-U1-12)
- 서버 동기화가 실패한 쓰기는 대기열에 남겨 다음 실행 때 보낸다 (U4 구현, 패턴은 여기서 정의)

### P-R3 멱등 작업
| 작업 | 멱등 근거 |
|---|---|
| 기기 등록 | 같은 ID + 같은 토큰 → 200 |
| 일일 정리 | "기준 시각보다 오래된 것 삭제"라서 반복해도 같은 결과 (BR-U1-15) |
| 마이그레이션 | `create ... if not exists`, 정책은 `drop policy if exists` 후 생성, 시드는 `on conflict do update` |
| 판정 교체 | RPC 안에서 "해당 범위 삭제 + 삽입"을 한 트랜잭션으로 (P-L2) |

### P-R4 실패 격리
- 일일 정리 작업은 "기기 정리"와 "공고 정리"를 따로 실행해 하나가 실패해도 다른 하나는 진행하고, 각각 `collect_runs`에 기록한다

## 2. 확장성 (Scalability): 적용하지 않음

규모가 고정되어(기기 ≤ 10, 공고 ≤ 2,000, NFR-U1-01) 큐·오토스케일·샤딩·읽기 복제를 두지 않는다. Vercel 함수와 Supabase는 관리형으로 필요한 만큼 동작한다. 규모 가정이 바뀌면 이 절을 다시 검토한다.

## 3. 성능 (Performance)

### P-P1 기준 데이터 메모리 캐시 (Q2=A)
| 항목 | 설계 |
|---|---|
| 대상 | 지구 목록, 공급유형 라벨(formal/plain), 공급유형 표준 요건, 연도별 기준표 |
| 위치 | Next 서버 함수 인스턴스 메모리 (모듈 수준 변수) |
| 수명 | **10분 TTL**. 만료 후 첫 요청이 다시 읽음 |
| 동시 요청 | 만료 시점에 동시 요청이 와도 읽기 1번만 하도록 진행 중인 Promise를 공유 |
| 일관성 | 시드 변경은 최대 10분 뒤 반영. 판정 재계산(S2)은 캐시를 쓰지 않고 항상 DB에서 읽음 (정확성 우선) |
| 캐시 안 하는 것 | 기기별 데이터(프로필·판정·구독): 항상 DB |

### P-P2 가벼운 인증
- 인증 = PK 조회 1번 + SHA-256 1번 + (1시간에 1번) `lastSeenAt` 갱신 (NFR-U1-04)
- 인증 조회 결과는 캐시하지 않는다 (삭제·모두 지우기 즉시 반영)

### P-P3 서버 컴포넌트 우선
- 레이아웃·헤더는 서버 컴포넌트. 클라이언트 컴포넌트는 `DeviceBootstrap`, `BottomNav`(현재 경로) 두 개만 (NFR-U1-06)

## 4. 보안 (Security, 최소 보호)

### P-S1 DB 전면 차단 + 서버 키 경유
- 모든 테이블 `enable row level security` + anon·authenticated의 테이블·시퀀스·함수 권한 회수
- DB 함수(RPC)도 `security definer`를 쓰지 않고, **service_role만 실행 권한**을 가진다
- 브라우저는 Supabase 키를 아예 받지 않는다

### P-S2 기기 토큰
- 생성: `crypto.getRandomValues(32바이트)` → base64url
- 저장: SHA-256 hex
- 비교: 길이가 같은 바이트 배열을 XOR 누적으로 비교 (상수 시간)

### P-S3 버전 붙은 금액 암호화
- 형식 `v{n}.{iv}.{ct}` (tech-stack-decisions §7)
- 복호화 시 `v{n}`으로 키 선택. 모르는 버전이면 오류(금액은 "모름"으로 처리하지 않고 판정 재계산을 그 기기만 건너뛰고 기록)
- 키 교체 시 재암호화는 일일 작업에 추가 (U2 NFR Design에서 상세)

### P-S4 등록 한도 (Q3=A)
| 항목 | 설계 |
|---|---|
| 규칙 | `POST /api/device`(새 등록일 때만) 처리 전, `devices.createdAt > now - 1시간` 개수가 **20 이상이면 429** `{ code: 'TOO_MANY_REGISTRATIONS', message: '잠시 후 다시 시도해 주세요' }` |
| 위치 | 등록 RPC 안에서 개수 확인과 삽입을 한 트랜잭션으로 (경쟁 상태 방지) |
| 재등록(같은 ID·토큰) | 한도에 세지 않음 |

### P-S5 로그 마스킹
- 공통 Logger가 `token`, `profile`, `enc*`, `money`, `p256dh`, `auth` 키를 가진 필드를 `[REDACTED]`로 바꾼다
- `deviceId`는 앞 8자리만 (NFR-U1-17)

### P-S6 입력 크기 제한
- 라우트별 최대 본문 크기 확인 후 초과 시 413 (등록 1KB, 프로필 32KB)

### P-S7 비밀 값 분리
- 서버 전용 환경 변수 모듈(`src/server/env.ts`)에서만 비밀 값을 읽고, 이 모듈을 클라이언트 컴포넌트가 import하면 빌드가 실패하게 한다 (`server-only` 패키지)

## 5. 관측성 (Observability)

| 패턴 | 설계 |
|---|---|
| 구조화 로그 | JSON 한 줄: `{ level, msg, requestId, route, deviceId8, status, ms }` |
| requestId | 요청마다 생성, 응답 헤더 `x-request-id`로 돌려줌 (오류 문의 시 확인용) |
| 헬스 체크 | `GET /api/health`: DB 가벼운 조회, 성공 `{ ok: true }` / 실패 503 |
| keepalive | GitHub Actions 매일 1회 호출, 실패 시 소유자 메일 (NFR-U1-08·09) |
| 작업 기록 | 정리·수집·발송 결과는 `collect_runs` (NFR-U1-10) |
