# U1 setup-data-platform — 비즈니스 규칙

> 규칙 ID는 테스트·코드 주석에서 참조한다 (예: `// BR-U1-03`).

---

## 1. 기기 등록 (Q4=B: 누구나 등록 가능)

| ID | 규칙 |
|---|---|
| BR-U1-01 | 기기는 처음 실행할 때 `deviceId`(UUID v4)와 `token`(암호학적 난수 32바이트, base64url 43자)을 **기기에서** 만든다 |
| BR-U1-02 | `POST /api/device { deviceId, token }`: 형식이 맞지 않으면 **400**. 서버는 `SHA-256(token)`만 저장하고 토큰 원문은 저장하거나 로그에 남기지 않는다 |
| BR-U1-03 | 같은 `deviceId`가 이미 있을 때: 저장된 해시와 `SHA-256(token)`이 **같으면 200**(같은 요청의 재전송, 멱등. NFR Design Q1 재시도 대비), **다르면 409**. 409를 받은 기기는 새 `deviceId`·`token`을 만들어 한 번 더 시도한다 (다른 기기의 ID를 가로채지 못하게 덮어쓰지 않음) |
| BR-U1-04 | 등록 시 `notifyHour = 9`, `notifyEnabled = true`, `lastSeenAt = now` |
| BR-U1-05 | **등록 제한 없음** (Q4=B). 대신 등록 요청 본문 크기 제한(1KB)과 형식 검증만 한다. 리스크는 §5에 기록 |

## 2. 기기 인증

| ID | 규칙 |
|---|---|
| BR-U1-06 | 기기 전용 API는 헤더 `x-device-id`, `x-device-token`이 모두 있어야 한다. 없거나 형식이 틀리면 **401 `AUTH_MISSING`** |
| BR-U1-07 | `SHA-256(token)`을 저장된 해시와 **상수 시간 비교**한다. 기기가 없으면 **401 `DEVICE_UNKNOWN`**, 해시가 다르면 **401 `TOKEN_MISMATCH`** |
| BR-U1-08 | 인증된 요청은 그 `deviceId`의 데이터만 읽고 쓸 수 있다. 다른 기기 ID를 경로·본문으로 받는 API는 만들지 않는다 |
| BR-U1-09 | `DEVICE_UNKNOWN`을 받은 기기는 **새 기기로 다시 등록**한다 (Q5=A). 이때 기기에 프로필이 남아 있으면(예: 서버에서 180일 미접속으로 삭제된 경우) **자동으로 다시 동기화**해서 사용자가 다시 입력하지 않게 한다 |
| BR-U1-10 | `TOKEN_MISMATCH`는 기기 데이터 손상으로 보고 BR-U1-09와 같이 처리한다. 다른 기기의 데이터에는 접근하지 않는다 |

## 3. 마지막 접속 시각

| ID | 규칙 |
|---|---|
| BR-U1-11 | 인증에 성공한 요청마다 `lastSeenAt`을 갱신하되, **이전 값과 1시간 이상 차이 날 때만** 쓴다 (쓰기 줄이기) |
| BR-U1-12 | 푸시 알림 발송·수신은 접속으로 세지 않는다. 알림을 눌러 앱이 열리고 API를 호출하면 접속으로 센다 |

## 4. 보관·삭제

| ID | 규칙 |
|---|---|
| BR-U1-13 | **미접속 기기 삭제 (Q3=A)**: `lastSeenAt`이 **180일**보다 오래된 기기는 Device를 삭제하고, 연쇄로 프로필·구독·판정·알림 이력을 모두 삭제한다 |
| BR-U1-14 | **공고 삭제 (Q2=B)**: `retentionBaseDate`(마감일 ?? 모집공고일 ?? 첫 수집일)가 **365일**보다 오래된 공고는 Notice를 삭제하고, 연쇄로 주택형·원천 공고·지구 연결·판정·알림 이력을 삭제한다 |
| BR-U1-15 | 정리 작업은 **하루 1번** 실행한다 (실행 위치·시각은 Infrastructure Design). 다시 실행해도 결과가 같다 (멱등) |
| BR-U1-16 | **모두 지우기 (US-20)**: `DELETE /api/device`는 인증된 기기의 Device를 삭제(연쇄 삭제)하고 **204**. 이미 없는 기기면 401 대신 **204**로 응답해 기기가 로컬 정리를 끝낼 수 있게 한다 (인증 실패 사유가 `DEVICE_UNKNOWN`일 때만) |
| BR-U1-17 | 북마크는 기기에 공고 요약 사본을 함께 저장한다. 서버에서 공고가 삭제된 북마크는 사본으로 보여주고 "공고 정보가 오래되어 삭제됐어요"를 표시한다 (U5에서 구현) |

## 5. 데이터 접근

| ID | 규칙 |
|---|---|
| BR-U1-18 | 모든 테이블에 RLS를 켜고 **anon·authenticated 역할의 모든 권한을 차단**한다. 접근은 서버 전용 키(Next 서버, Edge Function)로만 한다 (NFR-2.2) |
| BR-U1-19 | 브라우저 번들에 서버 전용 키·암호화 키를 넣지 않는다 (`NEXT_PUBLIC_` 접두사 금지 목록에 포함) |
| BR-U1-20 | API 오류 응답은 `{ code, message }` 형식. `message`는 사용자에게 보여줄 수 있는 쉬운 한국어 한 문장 (NFR-1.5) |
| BR-U1-21 | 서버 로그에 토큰, 프로필 값, 금액(평문·암호문)을 남기지 않는다 (NFR-2.5) |

## 6. 공고 무결성

| ID | 규칙 |
|---|---|
| BR-U1-22 | `SourceNotice`는 `(source, sourceNoticeNo)`가 유일하다. 같은 키로 다시 들어오면 갱신(upsert)한다 |
| BR-U1-23 | `Notice.dedupKey`는 유일하다. 서로 다른 소스의 원천 공고가 같은 `dedupKey`를 가지면 같은 대표 공고에 연결된다 (Q1=A, 키 생성 규칙은 U3) |
| BR-U1-24 | 대표 공고의 원문 링크는 `primarySource`의 링크를 쓴다. 우선순위는 공급 기관 원문 > 청약홈 > 마이홈 (U3에서 확정) |
| BR-U1-25 | 판정(`Judgement`)은 기기 × **대표 공고** 단위로 하나만 둔다 (최신 결과로 교체, 이력 없음) |

## 7. 인지된 리스크

| ID | 내용 | 대응 |
|---|---|---|
| RK-U1-1 | 등록 제한이 없어(Q4=B) 주소를 아는 제3자가 기기를 등록하고 데이터를 저장할 수 있음. 저장 공간·Gemini 사용량에는 영향이 거의 없음(요약은 공고 단위) | 가족 전용 비공개 운영(R2), 본문 크기 제한, 미접속 180일 삭제. 문제가 생기면 가족 코드(Q4 A안)를 나중에 추가할 수 있도록 등록 API를 한 곳에 둠 |
| RK-U1-2 | 판정은 1년 동안 남아 있어(Q2=B) 마감 공고의 판정도 보관됨 | 크기가 작음(기기 수 × 공고 수). 1년 뒤 공고와 함께 삭제 |
